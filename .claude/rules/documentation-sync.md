# 文档同步规则

每次修改代码后，**必须主动检查并更新受影响的文档和注释**，禁止等用户提醒。

## 文档分层策略

文档按"离代码距离"分为两层：

| 层级 | 存储位置 | 内容类型 | 过期风险 |
|------|---------|---------|---------|
| **代码注释** | 源码文件顶部 `@module` + JSDoc | 文件职责、函数签名、参数说明、依赖关系、消费者 | 最低（改代码时自然会看到） |
| **独立文档** | `docs/` 目录 | 跨模块交互图、架构决策（Why）、配置迁移表、开发规范/踩坑 | 中（需主动同步） |

**实现细节优先写入注释**，独立文档只保留"读单文件时看不到"的信息。

## 必须检查的场景

| 场景 | 更新范围 |
|------|----------|
| 文件重命名/移动/删除/拆分 | 所有引用路径（`grep` 旧路径）、`docs/` 文件索引、`CLAUDE.md` |
| 模块职责变更 | 对应 `docs/` 文档 + 源码顶部 `@module` 注释 |
| 新增/修改/删除函数或公共 API | 源码顶部注释（独立文档仅在有架构影响时才更新） |
| 修改配置结构（字段增删改） | `config.md` 迁移表 + `update.ts` 顶部注释 + 测试文件（`config-reset.test.ts`、`handle-app-update.test.ts`、`config-snapshot.test.ts`） |
| 新增/修改陷阱或易错点 | `.claude/rules/pitfalls.md`（索引）→ 对应领域文件 |
| 架构偏离（依赖关系变化、新模块） | 对应 `docs/` 架构图 + `CLAUDE.md` 目录结构表 |
| 编码风格/约定的变更 | `development.md` |
| 修改 `PRESERVE_FIELDS` | `config-reset.test.ts` 中 quick reset 断言 |
| 修改 `defaultConfig` 结构 | `config-snapshot.test.ts` 必需字段断言 |
| **修改 Reka 组件 CSS（`reka-ui.css`）** | **`reka-template.css`** — 模板必须与实际组件保持同步 |

## CHANGELOG 写作规则

`CHANGELOG.md` 是**面向用户**的版本说明，不是提交记录，也不是变更台账。

| 要写 | 不要写 |
|------|--------|
| 用户能感知的功能、交互、视觉变化 | 内部重构细节（Tabs 触发器重排、摊平实现、模块拆分） |
| 兼容性/迁移提示，以及用户该怎么做 | 测试、守卫、校验脚本、CI 规则、检查器新增条目 |
| 影响用户的技术迁移（一句话说明影响） | 依赖名与版本、文件路径、函数名、构建产物、代码评审过程 |
| 用户遇到的现象 + 现在的结果 | 根因分析（「因为缓存未取消…」「改为共用一层…」） |

写法要求：

- **合并同类项**：一个版本内同类改动聚合成条，修复项按模块或现象族合并（如「修复日历与资讯组件问题：A、B、C」），禁止一条一个内部迭代。
- **控制篇幅**：单个版本 4–8 条；单条不超过约 80 字，多个现象用「、」并列。
- **分类符号**：`+` 新增 / `-` 删除 / `^` 升级优化 / `#` 修复 / `!` 用户必须知晓的破坏性变更。`!` 要写清升级后需要用户做什么。
- **技术名词从简**：仅在影响用户时才保留（如「改用 tyme4ts 计算农历」「内容指纹改用原生 SHA-256」），不展开取舍过程。
- 大版本迭代结束后回头读一遍：**非开发者能否看懂？** 看不懂就说明写得太细。

## 检查清单

每次修改代码后，快速过一遍：
1. `grep` 旧路径/旧函数名，确认无遗漏引用
2. 修改的模块是否有 `@module` 顶部注释需要更新？
3. `docs/` 中是否有文档提及该模块或函数？（优先查对应文档索引表）
4. `CLAUDE.md` 的目录结构表是否需要更新？
5. 是否引入了新的已知陷阱需要记录到对应 `pitfalls-*.md`？
6. 是否涉及配置结构 / PRESERVE_FIELDS / defaultConfig？→ 检查测试文件是否需要同步更新
7. 是否修改了 Reka 组件 CSS？→ **必须检查 `reka-template.css` 是否需要同步更新**
