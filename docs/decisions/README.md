# 架构决策记录（ADR）

只记录**一次性做出的判断**：当时有哪些约束、选了哪条路、否掉了什么、代价是什么。

不记录现状。现状写在代码里，或者写在 `docs/architecture/` 里。这里的内容**只增不改**：决策被推翻时新建一条，标 `已取代（由 NNNN）`，原文保留。

这样做的原因很实际：一句话只要带上「在某年某月，因为 X，我们放弃了 Y」，它就永远为真；而「系统现在是这样」改变的那一刻就变成假话。

## 什么时候值得写一条 ADR

ADR 的价值在**少而重**，不在齐全。绝大多数"为什么"应该写在代码注释里，只有下面三个问题全部答"是"才开编号：

1. **有人会重新提出被否的方案吗？** 包括未来的自己、协作者、AI。会 → 继续问。
   如果答案是"没人会想推翻它，它就是个事实"，那它是注释，不是决策记录。
2. **推翻它的代价高吗？** 高到"线上事故 / 数据损坏 / 不可逆 / 法律风险"，才值得占一个永久编号。
   代价只是"改回来就行"的，写注释更合适。
3. **一句代码注释覆盖得了吗？** 覆盖得了 → 写注释，别开编号。
   覆盖不了的情况很典型：约束型决策。"不要抽这个函数""不要给这里加缓存"这类判断没有自然的落点——注释只能解释已有的代码，承载不了"不要做某事"。

三条全过才写。**宁可漏，不要凑数**——一条凑数的 ADR 会稀释真正重要的那几条，让人以后不愿意翻这个目录。

## 编号会断，这是正常的

编号是标识符，不是序号。合并、降级到代码注释、或撤回的条目会留下空号（例如 0008 已并入 `src/logic/shortcut/matcher.ts` 的注释）。**不要为了"整齐"重排编号**——任何外部引用（提交信息、代码注释、issue）都靠编号定位。

## 格式

```markdown
# NNNN. 一句话陈述这个决策

- 状态：已采纳 ｜ 已取代（由 NNNN）
- 日期：YYYY-MM-DD
- 相关代码：`src/...`

## 背景

当时面对什么约束。要具体到能让后来者判断"这条还成立吗"。

## 决策

做了什么。一句话能说清就别写两段。

## 被否的方案

每条都要写清为什么否。**这一节是给未来的 AI 看的**——它最容易重新提出已经否决过的方案。

## 后果

这个决策带来的限制、必须配套守住的约束、以及将来什么情况下应该重新评估。
```
